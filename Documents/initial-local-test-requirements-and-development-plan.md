## 1. 当前需求约束

本阶段目标不是做大规模商业化平台，而是先做一个可本地部署测试的小规模在线麻将产品。

明确约束如下：

- 初期最多支持 4 个在线人类玩家。
- 不需要高并发设计。
- 不需要广告入口。
- 不需要充值、支付、商城、会员等商业化入口。
- 用户不能自行注册账户。
- 用户账户由管理员统一创建。
- 初期先在本地部署测试。
- 支持 PC 浏览器访问。
- 支持移动端浏览器访问。
- 不足 4 名人类玩家时，由机器人补位。
- 服务端未来需要能运行在 Linux 下。

这些约束会明显降低第一版复杂度。开发重点应放在麻将规则、房间流程、实时同步、机器人补位和移动端可用性上。

## 2. 产品定位

第一阶段产品可以定义为：

一个小范围内使用的在线麻将测试系统，管理员预先创建玩家账号，玩家登录后进入房间进行麻将对局，不足 4 人时系统自动补机器人。

暂不做：

- 用户自助注册。
- 手机验证码登录。
- 第三方登录。
- 支付充值。
- 广告。
- 大厅匹配。
- 大规模并发。
- 复杂运营后台。
- 多玩法同时支持。

## 3. 初期功能范围

### 3.1 管理员功能

管理员功能第一版可以做得很轻：

- 管理员登录。
- 创建玩家账户。
- 修改玩家昵称。
- 重置玩家密码。
- 启用或禁用玩家账户。
- 查看当前房间和在线用户。

如果想进一步降低第一版开发量，也可以先不做完整管理后台，而是提供一组本地管理命令或初始化脚本创建账号。建议顺序如下：

1. 第一版用命令行脚本创建账号。
2. 本地联调稳定后，再补一个简单管理页面。

### 3.2 玩家功能

- 使用管理员分配的账号和密码登录。
- 登录后进入大厅。
- 创建房间。
- 输入房间号加入房间。
- 查看房间内座位。
- 准备。
- 房主开始游戏。
- 断线后重新登录并回到当前房间。

### 3.3 房间功能

- 一个房间最多 4 个座位。
- 初期同一时间可以只支持 1 个活跃房间。
- 后续可扩展为多个房间。
- 房主可以开始游戏。
- 开始游戏时，如果人类玩家不足 4 人，自动补机器人。
- 牌局结束后可返回房间继续下一局。

### 3.4 对局功能

第一版只实现一种麻将规则。建议选择一套规则边界较清晰、实现难度较低的玩法。

必须支持：

- 洗牌。
- 发牌。
- 摸牌。
- 打牌。
- 碰。
- 杠。
- 胡。
- 过。
- 基础结算。
- 回合计时。
- 超时自动出牌或托管。

可延后：

- 吃。
- 复杂番型。
- 杠上开花、抢杠胡、海底捞月等细分规则。
- 牌局回放。
- 观战。
- 排行榜。

是否支持“吃”取决于第一版选择的麻将玩法。如果选择不含吃牌的玩法，开发会简单很多。

### 3.5 机器人功能

第一版机器人目标是“能稳定打完一局”，不是“打得很强”。

基础策略：

- 能胡则胡。
- 能碰可按简单策略决定。
- 能杠可按简单策略决定。
- 出牌时优先打孤张、无组合价值的牌。
- 操作前延迟 0.5 至 2 秒，避免看起来像系统瞬间执行。

机器人也要走和真实玩家相同的服务端动作校验流程，避免出现特殊路径导致规则不一致。

## 4. 推荐技术方案

基于小规模、本地测试和后续 Linux 部署，建议采用简单单体架构。

```text
浏览器
  |
  | HTTP + WebSocket
  |
Node.js 服务端
  |
  | 读写
  |
SQLite 本地数据库
```

### 4.1 前端

推荐：

- React。
- TypeScript。
- Vite。
- Zustand 管理前端状态。
- CSS 自适应布局。
- Socket.IO Client 或原生 WebSocket。

前端页面：

- 登录页。
- 大厅页。
- 房间页。
- 牌桌页。
- 简单管理员页面。

### 4.2 服务端

推荐：

- Node.js。
- TypeScript。
- Fastify 或 Express。
- Socket.IO。
- SQLite。
- Prisma ORM。

选择理由：

- 单机部署简单。
- 本地测试方便。
- 不需要 Redis 和 PostgreSQL 也能满足初期 4 人在线。
- 后续如果要公网部署，可平滑迁移到 PostgreSQL。

### 4.3 数据库

初期使用 SQLite 即可。

主要数据表：

- `users`：玩家和管理员账号。
- `rooms`：房间。
- `games`：牌局记录。
- `game_events`：对局事件日志。

当前房间状态和牌局状态可以先放在服务端内存中，同时把关键事件写入 `game_events`，便于调试。

### 4.4 部署方式

本地测试阶段：

```text
npm install
npm run dev
浏览器访问 http://localhost:3000
手机访问 http://电脑局域网IP:3000
```

Linux 测试阶段：

- 使用 Docker Compose 或 PM2。
- 单个服务进程即可。
- SQLite 数据文件挂载到固定目录。
- 通过 Nginx 或 Caddy 反向代理。

公网正式部署时，再考虑：

- HTTPS。
- 域名。
- PostgreSQL。
- 备份。
- 日志和监控。

## 5. 简化后的系统模块

### 5.1 账号模块

职责：

- 管理员登录。
- 管理员创建玩家账户。
- 玩家登录。
- 密码加密存储。
- 登录态管理。

实现建议：

- 使用用户名 + 密码登录。
- 密码使用 bcrypt 或 argon2 哈希。
- 登录成功后签发 session 或 JWT。
- WebSocket 连接时校验登录态。

### 5.2 房间模块

职责：

- 创建房间。
- 加入房间。
- 离开房间。
- 准备。
- 开始游戏。
- 自动机器人补位。

简化规则：

- 初期可以只允许一个活跃房间。
- 玩家同一时间只能在一个房间内。
- 房间内最多 4 个座位。

### 5.3 牌局核心模块

职责：

- 表示牌、玩家、座位、牌墙、弃牌区。
- 执行发牌、摸牌、打牌。
- 判断可操作动作。
- 校验玩家动作。
- 推进回合。
- 判断胡牌和结算。

重要原则：

- 牌局核心不要依赖 WebSocket、数据库、页面。
- 它应该是一个可单独测试的 TypeScript 包。
- 所有对局动作必须由服务端调用牌局核心校验。

### 5.4 实时通信模块

职责：

- 管理 WebSocket 连接。
- 广播房间状态。
- 广播牌局状态。
- 接收玩家动作。
- 推送错误提示。
- 处理断线重连。

每个玩家收到的牌局状态必须经过过滤：

- 自己能看到自己的手牌。
- 不能看到其他真实玩家的手牌。
- 可以看到公开弃牌、碰杠信息、剩余牌数量。

### 5.5 机器人模块

职责：

- 作为虚拟玩家加入座位。
- 接收机器人视角状态。
- 选择合法动作。
- 延迟执行动作。

### 5.6 计时与托管模块

职责：

- 当前玩家操作倒计时。
- 超时自动打牌。
- 断线玩家自动托管。
- 玩家重连后恢复手动操作。

## 6. 推荐项目结构

```text
Mohjong/
  apps/
    web/                 # React 前端
    server/              # Node.js 服务端
  packages/
    mahjong-core/        # 麻将规则引擎
    shared/              # 共享类型和协议
  prisma/
    schema.prisma
  Documents/
    initial-local-test-requirements-and-development-plan.md
```

如果想进一步简化，也可以先做成一个 Vite + Node.js 的单体项目，但从维护角度看，仍建议把 `mahjong-core` 单独拆出来。

## 7. 开发计划

### 阶段 0：确认规则

目标：把第一版麻将玩法定死，避免开发中反复变更。

任务：

- 确认使用哪种麻将规则。
- 确认是否需要“吃”。
- 确认胡牌类型和计分规则。
- 确认是否有风牌、箭牌、花牌。
- 确认一局结束条件。

输出：

- `Documents/rule-spec.md`

建议工期：

- 1 至 2 天。

### 阶段 1：项目初始化

目标：搭建可运行的前后端项目。

任务：

- 初始化 pnpm workspace 或 npm workspace。
- 创建 `apps/web`。
- 创建 `apps/server`。
- 创建 `packages/mahjong-core`。
- 创建 `packages/shared`。
- 配置 TypeScript。
- 配置 ESLint 和基础格式化。
- 配置本地启动脚本。

输出：

- 本地能启动前端和后端。
- 浏览器能打开登录页。

建议工期：

- 1 天。

### 阶段 2：账号与管理员建号

目标：实现管理员统一创建账号，玩家不能自助注册。

任务：

- 设计用户表。
- 实现管理员初始化账号。
- 实现玩家账号创建。
- 实现登录接口。
- 实现密码哈希。
- 实现登录态。
- 实现简单管理员页面或命令行建号脚本。

输出：

- 管理员可以创建玩家账号。
- 玩家可以登录。
- 未登录用户不能进入大厅。

建议工期：

- 2 至 3 天。

### 阶段 3：麻将核心引擎

目标：实现可测试的牌局规则核心。

任务：

- 定义牌的数据结构。
- 实现牌墙和洗牌。
- 实现发牌。
- 实现摸牌。
- 实现打牌。
- 实现碰、杠、胡、过。
- 实现回合推进。
- 实现基础结算。
- 编写单元测试。

输出：

- 通过测试模拟完整牌局。
- 非法动作会被拒绝。

建议工期：

- 5 至 10 天，取决于规则复杂度。

### 阶段 4：房间与 WebSocket

目标：让 4 个浏览器窗口可以进入同一个房间并同步状态。

任务：

- 创建房间。
- 加入房间。
- 座位管理。
- 准备状态。
- WebSocket 鉴权。
- 房间状态广播。
- 断线重连。

输出：

- 多个浏览器窗口能看到同一个房间状态。
- 刷新页面后能恢复登录和房间状态。

建议工期：

- 3 至 5 天。

### 阶段 5：联机对局

目标：真实玩家可以完成一局基础麻将。

任务：

- 服务端接入 `mahjong-core`。
- WebSocket 接收玩家动作。
- 服务端校验动作。
- 广播每个玩家的视角状态。
- 前端展示手牌、弃牌、当前回合。
- 前端显示可执行操作按钮。
- 完成结算展示。

输出：

- 4 名人类玩家可以在本地完成一局。

建议工期：

- 5 至 8 天。

### 阶段 6：机器人补位

目标：不足 4 名人类玩家时可以开始游戏。

任务：

- 房主开始游戏时补齐机器人。
- 机器人接入统一动作流程。
- 实现基础出牌策略。
- 实现机器人操作延迟。
- 机器人动作广播给所有玩家。

输出：

- 1 至 3 名人类玩家 + 机器人可以完成一局。

建议工期：

- 3 至 5 天。

### 阶段 7：倒计时、托管和异常恢复

目标：避免牌局卡死。

任务：

- 当前操作玩家倒计时。
- 超时自动出牌。
- 断线后自动托管。
- 重连后恢复手动操作。
- 防止重复提交动作。
- 防止非当前玩家操作。

输出：

- 断线、刷新、超时不会导致牌局无法继续。

建议工期：

- 3 至 5 天。

### 阶段 8：PC 和移动端适配

目标：浏览器体验可用。

任务：

- PC 牌桌布局。
- 手机竖屏布局。
- 手机横屏布局。
- 手牌触控选择。
- 操作按钮防误触。
- 小屏幕信息压缩展示。

输出：

- PC 浏览器可正常玩。
- 手机浏览器可正常玩。

建议工期：

- 4 至 7 天。

### 阶段 9：本地测试部署

目标：在本机和局域网内测试。

任务：

- 配置一键启动脚本。
- 初始化管理员账号。
- 初始化 SQLite 数据库。
- 编写本地部署说明。
- 使用电脑浏览器和手机浏览器联调。

输出：

- 电脑访问 `http://localhost:3000`。
- 手机访问 `http://电脑局域网IP:3000`。

建议工期：

- 1 至 2 天。

### 阶段 10：Linux 测试部署准备

目标：为后续服务器部署做准备，但不在初期过度投入。

任务：

- 编写 Dockerfile。
- 编写 Docker Compose。
- 配置 SQLite 数据目录挂载。
- 配置环境变量。
- 编写 Linux 部署文档。

输出：

- Linux 下能用一条命令启动服务。

建议工期：

- 2 至 3 天。

## 8. 建议的第一版验收标准

第一版完成时，应满足：

- 管理员可以创建 4 个玩家账号。
- 玩家不能自行注册。
- 玩家可以登录。
- 玩家可以创建和加入房间。
- 1 至 4 名人类玩家都可以开始游戏。
- 不足 4 人时机器人自动补位。
- 能完整打完一局并显示结算。
- 刷新页面后能回到当前房间或牌局。
- PC 浏览器可用。
- 手机浏览器可用。
- 本地局域网内可访问。

## 9. 资源需求

### 9.1 开发环境

- Node.js LTS。
- pnpm 或 npm。
- SQLite。
- Chrome 或 Edge。
- 一台手机用于移动端测试。

### 9.2 本地测试环境

- 一台开发电脑即可。
- 手机和电脑连接同一个局域网。
- 不需要域名。
- 不需要 HTTPS。
- 不需要公网服务器。

### 9.3 后续 Linux 环境

- 1 台 Linux 服务器。
- 1 核或 2 核 CPU。
- 1 GB 至 2 GB 内存即可满足初期测试。
- 20 GB 磁盘。
- Ubuntu Server 22.04 LTS 或 24.04 LTS。

## 10. 当前推荐路线

最务实的路线是：

1. 先确认第一版玩法规则。
2. 先做本地单机联机版本。
3. 数据库先用 SQLite。
4. 不引入 Redis、PostgreSQL、Kubernetes、复杂网关。
5. 账号由管理员创建，先用脚本或简单后台。
6. 把牌局引擎和 WebSocket 同步做扎实。
7. 本地测试稳定后再准备 Linux 部署和域名。

这个路线能把初期复杂度控制住，也保留后续扩展空间。
