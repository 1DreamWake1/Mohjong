## 1. 产品目标

建设一个可通过 PC 浏览器和移动端浏览器访问的在线麻将网站。玩家可以创建房间、加入房间、在线对局；当人类玩家不足 4 人时，由机器人自动补位。服务端运行在 Linux 环境下，支持公网部署和域名访问。

建议先做 MVP 版本，确保核心闭环可用，再逐步扩展玩法、账号体系、排行榜、回放、观战、支付或运营能力。

## 2. MVP 功能范围

### 2.1 玩家功能

- 通过浏览器访问网站。
- 支持游客昵称登录，后续可扩展手机号、邮箱或第三方登录。
- 创建麻将房间。
- 输入房间号加入房间。
- 房主可开始游戏。
- 不足 4 名人类玩家时，由机器人补齐。
- 支持断线重连。
- 支持 PC 和移动端自适应布局。

### 2.2 对局功能

- 支持一套明确的麻将规则，建议第一版先选择“国标麻将简化版”或某一地方玩法。
- 发牌、摸牌、打牌。
- 吃、碰、杠、胡等操作。
- 回合计时，超时自动托管或由机器人代打。
- 对局结算。
- 房间内基础消息提示。

### 2.3 机器人功能

- 可替代空位玩家。
- 能根据当前手牌执行合法动作。
- 第一版机器人不追求高水平 AI，重点是保证牌局能稳定推进。
- 后续可加入策略评分、听牌判断、胡牌收益计算。

### 2.4 管理功能

- 第一版可以只做日志和基础后台接口。
- 后续再增加管理后台，例如在线房间、在线用户、异常牌局、封禁、配置玩法等。

## 3. 推荐技术架构

### 3.1 总体架构

```text
浏览器客户端
  |
  | HTTPS + WebSocket
  |
Nginx / Caddy 反向代理
  |
  | HTTP API + WebSocket API
  |
应用服务端
  |
  | 读写
  |
PostgreSQL / Redis
```

### 3.2 前端

推荐方案：

- React + TypeScript + Vite。
- 状态管理：Zustand 或 Redux Toolkit。
- UI：自定义 CSS 或 Tailwind CSS。
- 实时通信：原生 WebSocket 或 Socket.IO Client。
- 适配：CSS Grid、Flex、响应式断点、移动端触控事件。

前端主要模块：

- 登录 / 昵称设置页。
- 大厅页。
- 创建房间 / 加入房间。
- 牌桌页面。
- 对局状态展示。
- 操作按钮区。
- 断线重连与错误提示。

### 3.3 服务端

推荐方案一：Node.js + TypeScript。

- 框架：NestJS、Fastify 或 Express。
- WebSocket：Socket.IO 或 ws。
- 数据库：PostgreSQL。
- 缓存与房间状态：Redis。
- ORM：Prisma 或 Drizzle。
- 进程管理：PM2 或 Docker Compose。

推荐方案二：Go。

- HTTP 框架：Gin、Fiber 或标准库。
- WebSocket：gorilla/websocket 或 nhooyr/websocket。
- 数据库：PostgreSQL。
- 缓存：Redis。
- 部署：systemd 或 Docker Compose。

如果团队主要是 Web 开发背景，建议选 Node.js + TypeScript，前后端语言统一，开发效率更高。

### 3.4 实时通信

麻将属于强实时回合制游戏，核心通信建议使用 WebSocket。

HTTP API 负责：

- 登录。
- 获取大厅信息。
- 创建房间。
- 查询房间。
- 获取用户信息。

WebSocket 负责：

- 进入房间。
- 准备。
- 开始游戏。
- 发牌。
- 摸牌。
- 打牌。
- 吃碰杠胡操作。
- 广播牌局状态。
- 心跳。
- 断线重连。

### 3.5 数据存储

PostgreSQL 存储持久化数据：

- 用户表。
- 房间记录。
- 对局记录。
- 操作日志。
- 结算结果。

Redis 存储高频临时状态：

- 在线用户会话。
- 当前房间状态。
- 当前牌局状态。
- WebSocket 连接映射。
- 操作锁和倒计时。

第一版也可以先把牌局状态放在服务端内存中，但生产环境建议尽早引入 Redis，便于断线恢复、服务重启恢复和未来多实例扩展。

## 4. 核心服务模块

### 4.1 用户服务

职责：

- 创建游客用户。
- 维护用户在线状态。
- 处理断线重连身份校验。
- 后续支持正式账号体系。

### 4.2 房间服务

职责：

- 创建房间。
- 加入房间。
- 离开房间。
- 分配座位。
- 机器人补位。
- 房间销毁。

### 4.3 牌局引擎

职责：

- 初始化牌墙。
- 洗牌。
- 发牌。
- 管理回合。
- 校验合法操作。
- 计算胡牌、杠、碰、吃。
- 触发结算。
- 输出对每个玩家可见的牌局视图。

牌局引擎必须和网络层解耦。建议把它做成纯业务模块，输入玩家动作，输出新的牌局状态和事件。这样便于单元测试和后续复用。

### 4.4 机器人服务

职责：

- 接收当前机器人可见的牌局状态。
- 从合法动作中选择一个动作。
- 第一版实现基础策略：
  - 能胡则胡。
  - 能杠按规则判断是否杠。
  - 能碰时按手牌价值简单判断。
  - 打出孤张或低价值牌。
- 模拟人类延迟，避免瞬时操作影响体验。

### 4.5 对局计时服务

职责：

- 每个玩家操作有倒计时。
- 超时自动执行默认动作。
- 人类玩家断线后自动托管。
- 机器人按延迟自动出牌。

### 4.6 结算服务

职责：

- 判断胜负。
- 根据玩法计算番型和分数。
- 记录对局结果。
- 广播结算信息。

## 5. 前端页面架构

### 5.1 页面

- `/`：入口页，昵称登录或自动游客登录。
- `/lobby`：大厅，创建房间、输入房间号。
- `/room/:roomId`：房间等待页，展示座位和准备状态。
- `/game/:roomId`：牌桌页面。

### 5.2 牌桌布局

PC 端：

- 中央显示牌桌、牌墙、弃牌区、当前回合。
- 底部显示当前玩家手牌。
- 左、上、右显示其他玩家信息和弃牌。
- 右侧或底部显示操作按钮。

移动端：

- 当前玩家手牌固定在底部。
- 操作按钮靠近手牌。
- 其他玩家区域压缩显示。
- 弃牌区和提示信息优先保证可读性。

## 6. 软件与资源清单

### 6.1 开发资源

- 产品设计：玩法规则、页面流程、异常场景。
- UI 设计：牌面、桌面、按钮、移动端布局。
- 前端开发：React/Vue 或其他 Web 框架。
- 后端开发：实时通信、房间、牌局引擎、机器人。
- 测试：规则测试、并发测试、兼容性测试。
- 运维：Linux、域名、HTTPS、部署、监控。

### 6.2 服务器资源

MVP 阶段建议：

- 1 台 Linux 云服务器。
- 2 核 CPU。
- 4 GB 内存。
- 40 GB SSD。
- Ubuntu Server 22.04 LTS 或 24.04 LTS。
- 公网 IP。

用户增长后：

- 应用服务多实例。
- 独立 PostgreSQL。
- 独立 Redis。
- 对象存储保存日志、回放或静态资源。
- CDN 加速前端静态文件。

### 6.3 第三方资源

- 域名：阿里云、腾讯云、Cloudflare、Namecheap 等。
- SSL 证书：Let's Encrypt 免费证书。
- 日志与监控：Grafana、Prometheus、Loki，或云厂商监控。
- 错误追踪：Sentry。
- CI/CD：GitHub Actions、GitLab CI 或 Gitea Actions。

## 7. 推荐项目结构

```text
Mahjong/
  apps/
    web/                 # 前端网站
    server/              # 后端服务
  packages/
    mahjong-core/        # 牌局规则和引擎
    shared/              # 前后端共享类型
  Documents/
    online-mahjong-architecture-and-development-plan.md
  docker-compose.yml
  README.md
```

如果采用单仓库，建议把牌局核心逻辑放在 `packages/mahjong-core`，前端和服务端都依赖它的类型定义。这样可以减少前后端协议不一致。

## 8. 开发流程

### 8.1 阶段一：需求与规则确认

输出物：

- 产品需求文档。
- 玩法规则文档。
- 主要页面原型。
- WebSocket 事件清单。
- 数据表草案。

关键决策：

- 第一版支持哪种麻将规则。
- 是否允许游客直接玩。
- 房间是否需要密码。
- 是否记录完整牌局回放。
- 机器人策略复杂度。

### 8.2 阶段二：牌局引擎开发

先开发不依赖网络和数据库的牌局核心。

任务：

- 定义牌、玩家、房间、牌局状态。
- 实现洗牌、发牌、摸牌、打牌。
- 实现吃、碰、杠、胡判断。
- 实现回合推进。
- 实现结算。
- 编写大量单元测试。

这是项目最关键的部分。规则错误会直接影响用户信任。

### 8.3 阶段三：服务端开发

任务：

- 用户会话。
- 房间管理。
- WebSocket 网关。
- 房间状态广播。
- 断线重连。
- 机器人补位。
- 操作计时。
- 对局记录入库。

### 8.4 阶段四：前端开发

任务：

- 响应式页面框架。
- 大厅和房间页面。
- 牌桌 UI。
- WebSocket 连接管理。
- 状态同步。
- 操作按钮。
- 移动端适配。

### 8.5 阶段五：联调与测试

测试重点：

- 4 名人类玩家正常对局。
- 1 至 3 名人类玩家 + 机器人补位。
- 玩家刷新页面后重连。
- 玩家断网后托管。
- 多房间同时对局。
- 非法操作不能影响牌局。
- 移动端横屏和竖屏表现。
- 不同浏览器兼容性。

### 8.6 阶段六：部署上线

任务：

- 准备 Linux 服务器。
- 安装 Docker 和 Docker Compose。
- 配置 PostgreSQL、Redis、应用服务。
- 配置 Nginx 或 Caddy。
- 配置 HTTPS。
- 配置域名 DNS。
- 配置日志、备份和监控。

## 9. 部署方案

### 9.1 推荐部署拓扑

```text
用户浏览器
  |
  | https://mahjong.example.com
  |
Nginx / Caddy
  |
  | /api       -> server:3000
  | /socket.io -> server:3000
  | /          -> web 静态文件
  |
Docker Compose
  |-- web
  |-- server
  |-- postgres
  |-- redis
```

### 9.2 Docker Compose 服务

建议容器：

- `web`：前端构建后的静态资源，也可以直接由 Nginx 托管。
- `server`：Node.js 或 Go 后端服务。
- `postgres`：数据库。
- `redis`：缓存和房间状态。
- `nginx` 或 `caddy`：反向代理和 HTTPS。

### 9.3 域名绑定流程

1. 购买域名，例如 `example.com`。
2. 在 DNS 控制台添加解析：
   - 主机记录：`mahjong`
   - 记录类型：`A`
   - 记录值：服务器公网 IP
3. 等待 DNS 生效。
4. 在服务器反向代理中配置域名 `mahjong.example.com`。
5. 使用 Let's Encrypt 签发 HTTPS 证书。
6. 验证：
   - `https://mahjong.example.com` 可以打开网站。
   - WebSocket 连接使用 `wss://mahjong.example.com`。

### 9.4 Nginx 关键配置点

- 开启 HTTPS。
- HTTP 自动跳转 HTTPS。
- 正确代理 WebSocket：
  - `Upgrade` 请求头。
  - `Connection` 请求头。
- 静态资源设置缓存。
- API 设置合理超时。

使用 Caddy 会更简单，因为它可以自动申请和续期 HTTPS 证书。

## 10. 安全与稳定性

### 10.1 安全

- 所有请求使用 HTTPS。
- WebSocket 身份校验。
- 服务端必须校验所有玩家动作，不能信任前端。
- 防止一个玩家重复加入多个座位。
- 限制创建房间频率。
- 限制 WebSocket 消息频率。
- 记录异常操作日志。

### 10.2 稳定性

- 房间状态定期快照。
- 对局操作写入日志，便于回放和排查。
- 服务器进程崩溃后自动重启。
- Redis 和 PostgreSQL 定期备份。
- 关键错误接入告警。

## 11. 测试策略

### 11.1 单元测试

重点覆盖 `mahjong-core`：

- 发牌数量。
- 摸牌打牌。
- 吃碰杠胡合法性。
- 胡牌判断。
- 结算规则。
- 异常操作。

### 11.2 集成测试

- 创建房间。
- 多用户加入。
- 开始游戏。
- WebSocket 事件流。
- 断线重连。
- 机器人补位。

### 11.3 E2E 测试

使用 Playwright：

- PC 浏览器完整走一局。
- 移动端视口完整走一局。
- 刷新页面重连。
- 网络中断恢复。

### 11.4 压力测试

使用 k6 或 Artillery：

- 同时在线人数。
- 同时房间数量。
- WebSocket 消息吞吐。
- Redis 和数据库压力。

## 12. 里程碑建议

### M1：规则引擎可用

- 完成核心牌局状态和合法动作。
- 单元测试覆盖主要规则。
- 可以通过命令行模拟完整牌局。

### M2：本地多人联机

- WebSocket 房间可用。
- 4 个浏览器窗口能完成一局。
- 基础 UI 可操作。

### M3：机器人补位

- 1 至 3 名人类玩家可以开始游戏。
- 机器人能稳定完成合法动作。
- 超时托管可用。

### M4：移动端适配

- 手机浏览器可正常操作。
- 横屏和竖屏可用。
- 触控体验可接受。

### M5：测试服上线

- Linux 服务器部署。
- 域名和 HTTPS 可用。
- 日志、备份、监控完成基础配置。

### M6：正式发布

- 修复测试反馈。
- 增强规则和结算准确性。
- 完成基础运营与管理能力。

## 13. 风险与建议

### 13.1 主要风险

- 麻将规则复杂，容易出现边界错误。
- WebSocket 状态同步容易出现前后端不一致。
- 移动端牌桌交互空间有限。
- 机器人策略过弱会影响体验。
- 断线重连和异常恢复如果设计不好，会导致牌局卡死。

### 13.2 建议

- 第一版只支持一种明确规则，不要同时做多地玩法。
- 先把牌局引擎做扎实，再做 UI 美化。
- 每个玩家动作都记录事件日志，便于复盘问题。
- 所有牌局状态变更都由服务端裁决。
- 机器人第一版以稳定推进牌局为主，后续再增强智能程度。
- 前端只展示服务端下发的状态，不自行推导关键结果。
