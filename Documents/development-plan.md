# 在线麻将开发计划

## 1. 开发阶段概览

当前开发计划分为十九个阶段（含初始化）：

0. 项目初始化：monorepo 脚手架、共享类型、工具链配置。（已完成）
1. 完成麻将核心玩法算法和电脑玩家算法验证。
2. 完成服务端基础搭建 + 账号管理模块 + 登录前端 + 管理员用户管理页面。（已完成）

5. 合并麻将游戏核心业务算法，形成完整闭环。
6. 完善快速对局简单规则，明确胡牌来源、流局和结算展示。
7. 增加对局记录和事件持久化，支撑长期运行、调试和后续回放。
8. 增加历史对局查询 API，支持玩家查看自己的历史列表和事件详情。
9. 增加前端历史对局页面，支持玩家从大厅查看历史列表和事件详情。
10. 增强历史对局页面筛选和检索，支持按状态、结果和房间号定位记录。
11. 增强历史对局调试详情，展示结算快照、番型、胜者和胡牌信息。
12. 增加历史事件回放控件，支持按事件逐条播放历史对局时间线。
13. 增加完整牌桌状态快照回放，让历史回放可以复原每一步的玩家视角。
14. 完善真实多人房间，支持创建、加入、座位、准备、离开和 Bot 补位。
15. 增强进行中牌局恢复和房间生命周期管理，提升长期运行稳定性。
16. 增强规则配置化，逐步接入地方规则和更复杂结算。
17. 增加管理员对局后台，支持对局、房间、事件和玩家历史排查。
18. 完善 Docker 部署和长期运行能力，补齐容器化、备份、日志和生产配置。

## 2. 关键决策记录

以下技术决策在阶段 0 确定，各阶段遵循执行：

| 决策项              | 选择                | 理由                                                         |
| ------------------- | ------------------- | ------------------------------------------------------------ |
| 测试框架            | **Vitest**          | 与 Vite 生态一致，原生 TypeScript 支持，执行速度快           |
| CSS 方案            | **CSS Modules**     | 避免类名冲突，TypeScript 类型提示，适合组件化开发            |

| 密码哈希            | **bcrypt**          | 成熟的密码哈希库，防止彩虹表攻击                             |
| HTTP 客户端（测试） | **supertest**       | Fastify 集成测试标准工具                                     |
| Monorepo            | **pnpm workspaces** | 原生支持，无需额外依赖，适合当前规模                         |

## 4. 第一阶段：核心玩法算法与电脑玩家算法验证

### 4.1 阶段目标

完成麻将核心规则的算法验证，并验证电脑玩家可以按照规则参与对局。

本阶段不要求完成正式前端页面，也不要求接入服务器业务流程。重点是把麻将规则和电脑玩家算法做成可测试、可复用的核心模块。

### 4.2 功能点

- 定义麻将牌的数据结构（万/筒/条/风/箭，共 34 种 × 4 张 = 136 张）。
- 定义玩家、牌墙、手牌、弃牌区、公开组合等数据结构。
- 实现洗牌（Fisher-Yates）。
- 实现发牌（每人 13 张，庄家 14 张）。
- 实现摸牌。
- 实现打牌。
- 实现吃。
- 实现碰。
- 实现杠（明杠、暗杠、加杠）。
- 实现胡（基本胡牌判定：4 组面子 + 1 对雀头）。
- 实现过。
- 实现回合流转。
- 实现基础胜负判断。
- 实现基础结算。
- 实现 `RuleConfig` 配置接口，当前仅实现标准麻将配置。
- 实现电脑玩家合法动作选择。
- 实现电脑玩家出牌策略（优先打孤张、无组合价值的牌）。
- 实现 Vitest 单元测试覆盖所有公开 API。
- 实现 4 个 basicBot 自动模拟完整牌局测试。

### 4.3 规则要求

- 初期采用标准麻将规则，最小可用集：
  - **牌种**：万（1-9）、筒（1-9）、条（1-9）、风（东南西北）、箭（中发白），各 4 张。
  - **胡牌条件**：4 组面子（顺子或刻子）+ 1 对雀头，共 14 张。
  - **基本番型**（初期实现）：平和、立直（门前清）、断幺九、混一色、清一色、对对胡、七对子、混老头。
  - **计分**：初期采用简单计分（底分 + 番数 × 番分值），不实现复杂符数计算。
- 代码结构需要支持后续扩展地方规则。
- 后续需要支持四川麻将。
- 后续需要支持禁用"吃"等规则配置。

### 4.4 输出物

- 麻将核心算法模块（`packages/mahjong-core` 完整实现）。
- 电脑玩家算法模块（`packages/mahjong-core/src/bots/basicBot.ts`）。
- Vitest 单元测试覆盖。
- 4 bot 自动模拟牌局测试。
- 规则扩展设计文档（以 RuleConfig 接口 + 注释形式体现在代码中）。

### 4.5 验收标准

- 能通过 Vitest 测试脚本完成一局模拟对局。
- 电脑玩家能执行合法动作。
- 非法动作会被核心算法拒绝（reducer 返回错误）。
- 标准麻将基础流程可跑通（从发牌到胡牌/流局）。
- 规则模块没有和页面、数据库、服务器强绑定。
- `pnpm -F mahjong-core test` 全部通过。

## 5. 第二阶段：服务端基础 + 账号管理模块 + 登录和用户管理前端

> 此阶段合并了原"第二阶段（空壳服务器）"和"第三阶段（账号管理）"。
> 原第二阶段只搭一个返回 OK 的最小 Web 服务，价值有限且与第三阶段同属服务端工作。合并后可一次性完成 Fastify 骨架、Prisma 接入、User 表和登录 API，减少重复搭建。
> 为了让阶段验收能在浏览器中直接看到效果，登录页面和管理员用户管理页面也纳入第二阶段；原第三阶段缩小为玩家入口页面、路由保护细节和前端体验完善。

### 5.1 阶段目标

完成服务端应用搭建和最小可用账号管理闭环，包括 Fastify HTTP 服务、SQLite 数据库初始化、User 表实现、管理员和玩家账号管理 API、管理员登录页面、管理员用户管理页面，并确保可在 Ubuntu 虚拟机中通过浏览器完成登录和玩家账号管理操作。

### 5.2 功能点

- 初始化 Fastify 应用，配置 pino 日志。
- 配置 Prisma + SQLite，运行数据库迁移。
- 将账户信息持久化存储到 SQLite `User` 表，密码仅保存 bcrypt 哈希，不保存明文密码。
- 创建管理员账号（通过 seed 脚本或初始化命令）。
- 实现管理员登录 API。
- 实现玩家登录 API。
- 实现获取当前登录用户 API。
- 实现管理员创建玩家账号 API。
- 实现管理员删除玩家账号 API。
- 实现管理员重置玩家密码 API。
- 实现玩家列表查询 API。
- 实现密码 bcrypt 哈希存储和验证。
- 实现基础 JWT 登录态管理。
- 配置 CORS。
- 实现前端 API 客户端（封装 fetch、token 注入和错误处理）。
- 实现登录页面（用户名输入、密码输入、登录按钮、失败提示）。
- 实现管理员用户管理页面（玩家列表、搜索玩家、创建玩家账号、重置玩家密码、删除玩家账号）。
- 实现前端登录态存储（localStorage token）和最小路由切换。
- 在 Ubuntu 虚拟机中部署并验证浏览器可访问。
- 提供健康检查端点 `GET /health`。

### 5.3 数据表

`User` 表（Prisma schema）：

| 字段         | 类型            | 说明                |
| ------------ | --------------- | ------------------- |
| id           | Int (auto)      | 主键                |
| username     | String (unique) | 用户名              |
| passwordHash | String          | bcrypt 哈希         |
| role         | String          | "admin" 或 "player" |
| createdAt    | DateTime        | 创建时间            |
| updatedAt    | DateTime        | 更新时间            |

账户存储要求：

- 所有管理员和玩家账号均写入 SQLite 数据库。
- 密码入库前必须通过 bcrypt 哈希处理。
- 登录校验只比较 bcrypt 哈希结果。
- 代码和文档中不得记录真实生产密码；本地初始化管理员密码通过环境变量或初始化命令传入。
- SQLite 数据库文件、journal/WAL 文件不得提交到 Git。

### 7.4 shared 类型依赖（本阶段开始前需定义）

当前 `packages/shared/src/gameTypes.ts` 已有 `TileInfo`、`MeldInfo`、`DiscardPile`、`Action`、`OtherPlayerView` 和 `PlayerView` 基础类型。阶段四开始时需要先复核这些类型是否足够支撑 UI；如需增加展示字段，应优先保持字段面向"玩家视角"，不要把服务端内部状态暴露给前端。

```typescript
// packages/shared/src/gameTypes.ts（框架）
interface PlayerView {
  seatIndex: number;
  handTiles: TileInfo[]; // 自己的手牌（仅当前玩家有完整数据）
  otherPlayers: OtherPlayerView[];
  discardAreas: DiscardPile[]; // 各玩家弃牌区
  publicMelds: MeldInfo[]; // 公开的吃碰杠组合
  currentTurn: number; // 当前操作玩家 seatIndex
  availableActions: Action[]; // 当前玩家可执行的动作
  phase: GamePhase; // 当前阶段
}
```

类型补充原则：

- `PlayerView` 是游戏 UI 的唯一视角数据源。
- 页面不直接依赖 `mahjong-core` 的 `MahjongGameState`。
- 模拟数据、组件 props 和后续 Socket.IO `game:state` payload 使用同一套 shared 类型。
- 如果增加房间状态、座位风、事件消息等字段，字段必须能被第五阶段服务端 mapper 稳定生成。

- 梳理 `RuleConfig`，明确牌种、动作、胡牌规则、番型、计分模式和流局条件的配置边界。
- 将简单规则、标准规则整理为明确的规则预设。
- 增加规则选择字段，历史记录保存规则版本。
- 当前 `simple` 和 `standard` 预设均使用稳定名称及 `version: 1`；新建对局会将规则版本写入记录，历史详情展示对应版本，既有记录按版本 `1` 兼容。
- 核心包提供统一规则预设解析器；创建多人房间时可显式选择 `simple` 或 `standard`，大厅状态保存规则名称与版本，开局按房间预设创建牌墙和动作规则，非法预设由 HTTP 接口拒绝。
- `RuleConfig` 使用 `tileSet` 明确区分纯序数牌和标准牌组，并用 `drawCondition` 声明牌墙摸空流局；旧恢复快照中的 `useWinds/useDragons` 会在加载时自动归一化为新结构。
- 吃、碰、杠能力归入 `actions` 配置域，七对子归入 `winningPatterns`；规则 reducer、胡牌判断和计分统一读取新结构，旧快照恢复时删除顶层旧字段并迁移到新结构。
- 弃牌响应优先级归入 `claimPriority` 配置域，简单和标准规则默认保持“胡 > 碰/杠 > 吃”；响应者选择和同一玩家可见动作均读取当前规则，旧恢复快照会自动补齐默认优先级。
- 平和、立直、断幺九、混一色、清一色、对对胡、七对子和混老头归入 `enabledFans` 配置域；胡牌结构与番型计分分别配置，旧恢复快照默认保持现有番型全开行为。
- 各番型番数归入 `fanValues` 配置域，计分器负责识别番型但不再写死番值；旧恢复快照自动补齐当前平和/立直/断幺九 1 番、混一色 3 番、清一色 6 番等默认值。
- 计分模式、基础分和每番分值归入 `scoring` 配置域，`calculateScore` 默认从当前规则读取参数，同时保留调用级覆盖能力供测试和后续特殊结算使用。
- 本地 `pnpm dev` 启动前自动执行 `prisma migrate deploy`，避免数据库 schema 落后导致登录或启动恢复失败；SQLite 新增非恒定默认值字段时使用重建表迁移，兼容已有数据升级。
- 扩展番型和计分测试，避免新增规则影响现有简单快速对局。
- 设计四川麻将所需能力：缺门、换三张、血战到底、刮风下雨、查叫等，先形成接口和阶段拆分。
- 暂不一次性实现所有地方规则，优先保证配置边界清晰、回归测试稳定。

### 19.3 验收标准

- 简单规则和标准规则可以通过规则预设明确区分。
- 禁吃、牌种范围、计分模式不需要在服务端流程中硬编码。
- 新增规则配置不会破坏现有快速对局和历史记录。
- 核心规则测试覆盖不同规则预设的关键差异。
- `pnpm typecheck`、`pnpm lint`、`pnpm test`、`pnpm build` 通过。

## 20. 第十七阶段：管理员对局后台

### 20.1 阶段目标

在现有管理员玩家管理基础上，增加对局运维和调试入口，让管理员可以查看房间、历史对局、玩家对局记录和异常事件。

阶段状态：已于 2026-07-20 完成。

### 20.2 功能点

- 管理员页面增加对局管理入口。
- 服务端提供管理员历史对局列表和详情 API。
- 已增加 `GET /admin/games` 和 `GET /admin/games/:roomId`，管理员可跨玩家读取对局摘要、事件与结算详情，普通玩家访问返回 403。
- 管理员对局记录返回玩家 ID，并在用户仍存在时返回用户名；后台对局页可按房间号、玩家名、玩家 ID 和状态筛选。
- 后台对局页已支持按结束原因和开始日期范围筛选，详情展示开始/结束时间、胜者、胡牌方式、番型、番数、总分和完整事件列表。
- 管理员可选择带视角快照的历史事件，复用牌桌组件检查该事件发生时的脱敏牌桌状态；异常结束事件会在同一详情时间线中展示。
- 已增加 `GET /admin/active-rooms`，返回等待、进行中和待清理房间；座位连接状态区分在线、断线、Bot 和空位，同一玩家多 Socket 连接使用引用计数避免误判下线。
- 已增加 `GET /admin/persistence-diagnostics`；持久化队列失败会同时写入结构化日志和独立内存诊断缓冲区，按最新优先保留本次进程最近 200 条，不依赖故障中的数据库写入路径。
- 支持按玩家、房间号、状态、结束原因、时间范围筛选。
- 展示单局事件、结算快照、回放入口和异常结束信息。
- 展示当前活跃房间和在线/断线玩家状态。
- 权限隔离：玩家不能访问管理员对局后台。

### 20.3 验收标准

- 管理员可以查看全量历史对局和单局详情。
- 管理员可以按玩家或房间号定位对局。
- 管理员能看到异常结束和持久化失败相关信息。
- 玩家访问管理员对局 API 和页面会被拒绝。
- `pnpm typecheck`、`pnpm lint`、`pnpm test`、`pnpm build` 通过。
