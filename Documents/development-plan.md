## 3. 阶段 18：部署和长期运行

目标是将项目推进到可重复部署、可监控、可备份恢复和可安全退出的单实例运行形态。

### 18A 容器化与统一入口

状态：已完成。

- Server 和 Web 多阶段镜像，固定基础镜像和 pnpm 版本。
- Nginx 同源提供静态页面、HTTP API 和 Socket.IO。
- Compose 编排 Server、Web 和 SQLite 命名卷。
- 启动时自动执行 Prisma migration。
- 容器以非 root 用户运行，不打包本地数据和开发产物。

### 18B 健康检查与进程生命周期

状态：已完成。

- `/health` 存活探针与 `/ready` 就绪探针。
- readiness 检查房间恢复状态和数据库连接。
- Compose 基于真实 HTTP 探针编排健康依赖。
- `SIGTERM`、`SIGINT` 停止新任务并关闭 Socket.IO、计时器和清理任务。
- 等待持久化队列、断开 Prisma，并限制最大停机时间。
- 生命周期过程使用结构化日志记录。

### 18C SQLite 备份、恢复与升级回滚

状态：已完成。

- 数据库与备份使用独立持久化卷 `mahjong-data` 和 `mahjong-backups`。
- `dbbackup` 命令使用 SQLite `VACUUM INTO` 在线一致性备份，不直接复制活动数据库。
- 备份元数据记录时间、应用版本和 migration 列表，按 `BACKUP_KEEP` 保留清理。
- 恢复前保留当前数据库为 `*.pre-restore-<时间戳>`，恢复后执行完整性和 migration 检查。
- Server 启动迁移前自动备份（`BACKUP_ON_BOOT`），失败可回滚旧镜像并恢复备份。
- 部署手册包含升级前备份、镜像升级、健康验证、失败回滚和新数据卷演练流程。

验收：备份和恢复均有可执行命令；恢复后的关键数据可查询；失败升级能回退到可用版本。

### 18D 生产配置与安全基线

状态：已完成。

- `NODE_ENV=production` 时校验 `AUTH_TOKEN_SECRET`（≥32 字符）和 `DATABASE_URL`，缺失或不合规直接拒绝启动。
- 同源部署默认关闭 CORS，`CORS_ORIGIN` 可配置来源白名单；Fastify 请求体上限 64KB。
- 登录接口、Socket 连接和游戏动作均接入滑动窗口限流，阈值可用环境变量调整。
- nginx 增加 `X-Content-Type-Options`、`X-Frame-Options`、`Referrer-Policy` 和 CSP 安全响应头。
- JWT 使用 `timingSafeEqual` 校验签名，补充畸形、过期、篡改和非法 base64 输入测试。
- 管理员密码在开发环境至少 6 位、生产环境至少 12 位，并拒绝常见弱密码；文档明确 Token 存储风险。

验收：缺失必要配置时拒绝启动，常见暴力请求受到限制，敏感数据不进入日志和镜像。

### 18E 自动化验收与运行手册

状态：已完成。

- GitHub Actions CI 在 push/pull request 时执行安装、Prisma 生成、格式、类型、Lint、测试和生产构建（`check` job）。
- `smoke` job 构建 Docker 镜像并执行迁移、存活/就绪探针、管理员登录和 Socket.IO 冒烟脚本。
- `e2e` job 使用 Playwright 覆盖登录、多人建房/加入/准备/开局、历史查询和结算明细，使用独立 e2e 数据库。
- 部署手册补充 CI 自动化说明；环境准备文档补充 e2e 验证命令。

验收：全新 Linux 环境能够只依据文档完成部署和关键流程验证。

### Render Free 演示版

状态：已完成基础适配。

- `Dockerfile.render` 将 React 静态资源和 Fastify、Socket.IO 合并到一个 Web Service。
- `render.yaml` 可作为 Render Blueprint，自动设置端口、健康检查和临时 SQLite。
- 启动时执行 Prisma migration，并在 `DEMO_SEED=1` 时预置四个演示玩家账号。
- Render 免费实例的本地文件系统会在重启、重新部署或休眠后丢失，且实例会自动休眠；仅用于功能演示。

详细步骤和账号见 [deployment.md](./deployment.md) 的 Render Free 演示版章节。

## 4. 后续阶段

### 阶段 19A：四川麻将基础规则预设

状态：已完成。

- 核心新增独立 `sichuan` 规则预设，使用 108 张万、筒、条牌墙。
- 四川预设禁用吃，启用碰和杠，使用独立的四川计分模式、封顶和最低番配置。
- 该预设已在房间创建界面开放，牌桌支持换三张、定缺和血战基础流程。
- 简单规则和标准规则继续保持原有默认行为。

### 阶段 19B：换三张、定缺与出牌约束

状态：已完成。

- 已完成换三张和定缺开局状态机，四位玩家提交后才进入摸打阶段。
- 已完成定缺花色记录、定缺牌优先出牌和核心 reducer 的非法出牌拦截。
- 手中仍有定缺花色时不能声明胡牌，Bot 会优先清理定缺牌。
- Bot 已能根据花色数量和牌张连接度选择换三张，并自动选择较少的定缺花色。
- 四川模式已接入房间规则选择，牌桌支持换三张选择和定缺操作。

### 阶段 19C：血战到底多赢家状态

状态：已完成（基础版）。

- 已完成四川模式多赢家基础状态：胡牌玩家标记为退出，后续回合跳过该玩家。
- 前两位玩家胡牌后牌局继续，第三位玩家胡牌后结束当前牌局。
- 已胡状态已同步到核心 PlayerView、服务端房间视图和牌桌玩家信息。
- 四川弃牌响应支持多个胡牌玩家依次确认同一张牌，响应结束后再恢复正常摸打。
- 每位四川赢家保留独立 `winRecords`，记录赢家座位、胡牌方式、胡牌牌张和番型结果。
- `winRecords` 已映射到实时 PlayerView，牌桌侧栏显示每位赢家的方式和分数。
- `winRecords` 已写入结算 `resultSnapshot`，历史记录和管理端详情可恢复多赢家明细。
- 四川杠分已写入结算 `resultSnapshot`，历史记录和管理端详情可恢复杠分收支。
- 基础查叫结果已写入结算 `resultSnapshot`，历史记录可查看各座位听牌集合及最高番/分数。
- 基础查叫结果已同步到实时结算视图，牌局结束时可直接查看各座位听牌和最高分。
- 血战结束事件会汇总多位赢家和杠分，不再只显示最后一位赢家。
- 服务端 Bot 回合已覆盖换三张和定缺阶段，并会主动寻找尚未提交的 Bot 座位，四川房间不会因开局阶段停滞。
- Socket 调度已覆盖四川开局阶段，Bot 会按延迟自动完成换三张和定缺，单人模式仍不会为真人安排超时。
- 历史结算快照会校验赢家和查叫座位范围，避免异常数据污染结算视图。
- 实时结算优先使用全局查叫结果，兼容旧数据的个人听牌回退展示。
- 四川模式已接入大厅创建入口，牌桌支持换三张三牌选择和定缺操作。
- 牌局流局时可计算未胡玩家的基础听牌集合，并在结算视角展示。
- 四川暗杠、加杠和点杠已记录基础杠分收支，并同步到牌桌玩家信息。
- 标准和简单规则仍保持单赢家立即结束。
- 已完成基础查叫牌张、最高番和最高分展示；地方玩法的查叫转移算法留待规则扩展阶段。

### 阶段 19D：四川模式产品入口

状态：已完成。

- 服务端房间接口允许创建 `sichuan` 规则房间。
- 大厅提供四川麻将规则选项，房间列表和牌局页面显示规则名称。
- 牌桌支持换三张选择确认和定缺操作，开局流程可由真人完成。
- 四川模式已具备从建房、开局、对局到结算和历史恢复的基础闭环。

阶段 19 验收结论：基础四川麻将流程已完成，标准/简单规则回归保持通过；抢杠胡、杠上花、杠上炮等地方玩法变体不纳入本阶段基础版范围。

### 阶段 20A：杠上花与杠上炮

状态：已完成基础接入。

- 杠后补牌自摸会记录为“杠上花”。
- 杠后出牌被其他玩家胡会记录为“杠上炮”。
- 特殊胡牌来源已同步到实时赢家明细、历史记录和管理端详情。
- 抢杠胡需要独立的加杠响应窗口，列入阶段 20B。

### 阶段 20B：抢杠胡响应窗口

状态：已完成基础接入。

- 加杠前会检测其他玩家是否可以用该牌胡牌。
- 抢杠胡玩家按响应顺序获得 `胡/过` 操作，过牌后才完成加杠。
- 抢杠胡复用四川多赢家流程，并记录 `robGang` 结算来源。
- 抢杠胡未发生时，加杠仍按原有补牌和杠分流程执行。

阶段 20 验收结论：杠上花、杠上炮和抢杠胡基础流程已完成，相关来源会同步实时视图、历史快照和管理端详情。

### 阶段 21：四川终局结算

状态：已完成。

- 牌墙耗尽时进入统一的四川终局结算流程，保留杠分并生成最终座位分数。
- 已实现查叫转移：未听牌玩家按听牌玩家最高可得分数逐一支付，转移明细记录付款方、收款方和分值。
- 已实现基础花猪退税：仍保留定缺花色的玩家向其他未胡玩家各支付 4 分；花猪不重复参与查叫支付。
- 终局分数和转移明细写入核心状态、实时牌桌、历史快照和管理端详情。
- 补充核心规则测试，覆盖花猪转移、分数守恒和历史快照兼容字段。

阶段 21 验收结论：四川流局不再只有听牌展示，查叫和花猪分数会形成可追溯的终局结算结果；标准、简单规则不受影响。

- 实现与架构边界一致，没有绕过服务端规则或玩家视角过滤。
- 风险对应的单元、集成或端到端测试通过。
- `pnpm typecheck`、`pnpm lint`、`pnpm test` 和 `pnpm build` 通过。
- 用户可见或运行方式变化已同步文档。
- 不提交数据库、密钥、日志、备份和生成产物。
